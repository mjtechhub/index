Enterprise Network Troubleshooting Case Studies

The best way to master the Network Troubleshooting Workflow is by studying realistic enterprise scenarios. These fictional case studies demonstrate how to apply evidence-based methodology rather than relying on guesswork.

Case 1: The "Slow Internet" Saturation

  • Symptoms: Users across the entire office complain that web browsing is extremely slow and VoIP calls are robotic every afternoon between 2:00 PM and 4:00 PM.
  • Initial Hypothesis: The ISP is dropping traffic or the firewall is failing.
  • Evidence Collected: The engineer checks the SNMP Monitoring dashboard. The 500 Mbps WAN link is sitting exactly at 100% utilization during those hours. NetFlow data reveals that a single internal storage server is transmitting 450 Mbps of data to an offsite cloud backup provider.
  • Root Cause: A massive backup job is saturating the WAN, leaving no Bandwidth for users and causing extreme Packet Loss for VoIP.
  • Resolution: The engineer reschedules the backup job for 2:00 AM and applies a Traffic Shaping policy to cap backup traffic at 100 Mbps.
  • Lesson Learned: Measure utilization before blaming the ISP.

Case 2: The Missing Trunk VLAN

  • Symptoms: A new team moved to the 3rd floor. They plugged into the access switch and received correct IPs for VLAN 40 via DHCP, but they cannot ping the Default Gateway or access any servers.
  • Evidence Collected: The engineer verifies the users have the correct IP config. Users in VLAN 40 on the 2nd floor are working perfectly. A ping from the 3rd-floor switch management interface to the Gateway succeeds.
  • Tests Performed: The engineer checks the uplink trunk port connecting the 3rd-floor switch to the Core router. The configuration reads: switchport trunk allowed vlan 10,20,30.
  • Root Cause: VLAN 40 was never allowed to traverse the physical uplink trunk.
  • Resolution: The engineer adds VLAN 40 to the trunk allowed list.

Case 3: The Ghost VPN Tunnel

  • Symptoms: A Site-to-Site VPN is established to a partner company. The firewall dashboard shows Phase 1 and Phase 2 are "UP". However, no servers can communicate across the tunnel.
  • Evidence Collected: Routing tables show a valid route pointing traffic for the partner subnets into the VPN tunnel.
  • Tests Performed: The engineer runs a packet capture on the firewall's WAN interface. They see traffic leaving their site destined for the partner, but the Source IP is their Public WAN IP, not the internal private IP of the server.
  • Root Cause: A broad NAT policy was incorrectly translating the internal server traffic before it entered the tunnel. The partner firewall dropped the unrecognized public IP.
  • Resolution: The engineer creates a NAT Exemption (No-NAT) rule for traffic destined to the VPN zone.

Case 4: The Wi-Fi Video Glitch

  • Symptoms: Executives report that video conferencing (Zoom/Teams) is constantly freezing and dropping audio while in the boardroom.
  • Initial Hypothesis: The network is dropping packets.
  • Evidence Collected: The engineer tests from a hardwired desktop in the boardroom; video works flawlessly. They test on a laptop via Wi-Fi; video freezes.
  • Tests Performed: Using an RF scanner, the engineer discovers the boardroom Access Point is operating on a 2.4GHz channel heavily congested by neighboring office networks and Bluetooth devices, causing massive Jitter.
  • Root Cause: Wireless RF interference and half-duplex contention.
  • Resolution: The engineer disables the 2.4GHz radio in the boardroom and forces all corporate laptops to use the cleaner 5GHz band.

Case 5: The "Network" Is Slow

  • Symptoms: Developers complain that a new database query is taking 30 seconds to return results, claiming "network latency is terrible today."
  • Evidence Collected: The network engineer reviews monitoring. The links are at 5% utilization. A continuous ping from the developer's PC to the database server shows a flawless 1ms Latency with 0% packet loss.
  • Tests Performed: A packet capture shows the developer's PC sending the SQL request, the network delivering it instantly, and the database server silently churning for 29.9 seconds before finally sending the reply packet back.
  • Root Cause: A poorly optimized SQL query missing a database index. The network is perfectly healthy.
  • Lesson Learned: Never accept the blame for a "slow network" without evidence. Application response time is not network latency.
