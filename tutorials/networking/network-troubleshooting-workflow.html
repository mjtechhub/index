Network Troubleshooting Workflow

Intermediate 10 min read

Effective network troubleshooting relies on a structured, layer-by-layer methodology (often following the OSI Model) rather than guessing. Follow this workflow to isolate and identify connectivity issues efficiently.

The Initial Isolation Phase

Before touching the command line, ask critical isolation questions:

  • Is it happening to just one device, or multiple?
  • Is it affecting an entire VLAN or physical switch?
  • Is it limited to one site or the whole company?
  • Is the user failing to reach one specific hostname, or everything?
  • Is it failing on one protocol (e.g., HTTPS works, but SSH fails)?

Step-by-Step Diagnostic Workflow

STEP 1 — Physical / Wi-Fi Layer

Check the hardware and link status. Is the Ethernet cable plugged in securely? Are the link lights active on the switch port and PC? For wireless, check the SSID and signal strength.

STEP 2 — Local IP Configuration

Verify what the OS actually thinks its networking state is. Check the IP address, subnet mask, gateway, and DNS servers.

ipconfig /all

If you see an APIPA address or a blank config, refer to the DHCP troubleshooting guide.

STEP 3 — Local Stack

Ensure the local TCP/IP stack and NIC are functioning properly. (Note: Modern OSs sometimes skip this, but it's a solid fundamental step).

ping 127.0.0.1

STEP 4 — Local Network (Gateway Reachability)

Can you reach your own router? Ping the Default Gateway IP found in Step 2. If this fails, the problem is on the local switch, VLAN, or the gateway is down.

ping <gateway-ip>

You can also check your local ARP cache to verify MAC address resolution:

arp -a

STEP 5 — Routing

If you have multiple network interfaces or VPNs, check the routing table to ensure traffic is leaving out the correct interface.

route print

STEP 6 — Remote IP Connectivity

Can you route outside the local network? Ping a known, highly reliable public IP address (assuming ICMP is allowed out of your network).

ping 1.1.1.1

If the gateway responds but remote IPs do not, check the firewall, ISP connection, or external routing.

STEP 7 — DNS Resolution

If pinging an IP works but browsing to a website fails, test name resolution. See the DNS troubleshooting guide for details.

nslookup example.com
Resolve-DnsName example.com

STEP 8 — Path Tracing

If connectivity is dropping somewhere in the middle, or routing in a complex WAN is suspect, trace the path to see where it stops or loops.

tracert example.com
pathping example.com

STEP 9 — Service / Port Layer

Just because you can ping a server does not mean the application service (like a web server or database) is running and allowed through the firewall. Test specific TCP ports.

Test-NetConnection example.com -Port 443

STEP 10 — Application Layer

If all lower layers succeed, the issue resides in the application itself. Check web browsers, application proxies, host-based firewalls, SSL certificates, or the service configuration on the destination server.
