DHCP Troubleshooting Guide

DHCP (Dynamic Host Configuration Protocol) automates IP address assignment. When it fails, clients lose connectivity. Common symptoms include: no IP address, receiving a wrong subnet/gateway/DNS, duplicate IP conflicts, or lease renewal failures.

Troubleshooting Sequence

1. Verify Physical & Layer 2 Connection

Ensure the cable is plugged in, the Wi-Fi is connected, and the switch port is active. DHCP relies on broadcast traffic; if Layer 1 or Layer 2 is down, DHCP cannot work.

2. Check IP Configuration & APIPA

Run the following command to check the current state:

ipconfig /all

Or in PowerShell:

Get-NetIPConfiguration

If you see an IP address starting with 169.254.x.x (part of the 169.254.0.0/16 range), it means the device assigned itself an APIPA (Automatic Private IP Addressing) address because it couldn't reach a DHCP server. Do not claim APIPA always proves the DHCP server itself is down. The failure could be the local network, the VLAN assignment, a misconfigured DHCP relay, or the client itself.

3. Determine DHCP vs Static

Ensure the device is actually configured to "Obtain an IP address automatically" and hasn't been manually assigned a conflicting static IP.

4. Release and Renew

Force the client to drop its current lease and request a new one.

ipconfig /release
ipconfig /renew

5. Verify the DHCP Relay / IP Helper

Because DHCP uses broadcast messages, the requests do not cross routers by default. If the DHCP server is on a different subnet than the client, the router interface for the client's subnet MUST be configured as a DHCP Relay (or IP Helper). If this is missing or misconfigured, clients won't get IPs.

6. Check the DHCP Server & Scope

On the server side:

  • Verify the DHCP Service is running.
  • Check the scope for available addresses (is the scope 100% full?).
  • Ensure there are no excessive rogue reservations or conflict detections pausing the service.
